## 术语与实质修正

- delivery / deployment / release 分别按语境使用“交付／部署／发布”；continuous delivery 为“持续交付”，continuous deployment 为“持续部署”。第78行仍保留原书把自动部署描述为 CD 极致状态的说法，不另行重写其概念体系。
- release train 统一为“发布列车”，指按固定节奏发车的发布机制；flag guarding 为“用标志保护”，明确功能是否进入构建、运行时是否启用，以及配置更新与二进制包发布相互独立。
- canarying 为“金丝雀发布”（208行），用于少量流量中的稳定性观察，不能替代新版效果与旧版效果的比较。212行保留重新发布旧版作为安慰剂基线的部署 A/B 测试。
- rollback / rollforward 为“回滚／前滚”；88行的 regression testing 为“回归测试”，不是回滚。84行 culprit finding 为“致错变更定位”，branch 为“分支”。
- release qualification 为“发布验证”；testing tracks 为“测试通道”；change-neutral releases 按216行上下文译为“不改变功能行为的发布”；dry-run verification 为“试运行验证”。这些译法不改变原书中的流程和限定。
- 78行恢复“缺陷未在测试中发现”的否定；88行恢复“几乎每次”及每个版本50小时的手工回归测试。
- 102、106、110行区分部署二进制包、启用新功能、发布新闻稿，恢复先部署、后公开宣布，以及在新闻稿发布前启用功能的时序。
- 120行恢复“构建二进制包、集成数据、测试”三个步骤；124行保留每隔一天向生产环境发布；152、156行修正截止点、选择性合并、重新生成并测试二进制包及取气球的含义。
- 178行修正修饰关系：只向设备交付有用户价值的代码，而非挑选“有价值的设备”。188行 clients 是客户端，qualifying a release 是发布验证。
- 226行将“四分之一新特性”改为“一季度新功能和缺陷修复”；230行 recency 是变更刚发生不久，不是变更频率；234行恢复“极少有功能值得推迟整个发布”的判断。
- 252行的 in or out 指哪些变更可以纳入发布，不是判断发布是否成功。提要逐项对照英文重审，保留各项条件和目的。
