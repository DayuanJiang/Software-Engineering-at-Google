# 第一章术语补充

本表针对第一章的实际上下文，补充准备阶段的核心术语表。
这些选择先用于样稿，待样稿风格确认后再决定是否推广到其他章节。
行号沿用原章节，未因本次修改变化。

| 英文 | 本章译法 | 语义边界与依据 |
| --- | --- | --- |
| programming integrated over time | 编程在时间上的积分 | 保留积分隐喻，与后面的立方体、正方形、距离和速度相呼应。第19–21行。 |
| life span | 生命周期／预期使用寿命 | 不是单次运行时间；原文脚注明确区分执行与维护。第23–29行。 |
| execution lifetime | 执行生命周期 | 修正原译“开发生命周期”。第27–29行。 |
| maintenance lifetime | 维护生命周期 | 代码继续构建、执行、维护和提供价值的时间。第27–29行。 |
| sustainability | 可持续性 | 本章指在所需使用期内应对必要变更的能力，不等于禁止变更或环境议题。第31–33行。 |
| scalability / scalable | 可扩展性／可扩展 | 关注规模增大时成本和工作量如何增长，不统一改成“扩容”。第224–246行。 |
| sublinear / superlinear | 次线性／超线性 | 保留增长关系，不分别简化成“低”或“高”。第224、244、273行。 |
| Hyrum’s Law | 海勒姆定律 | 沿用本书现有译名。定律讨论所有可观察行为，不只公开承诺的接口。第122–146行。 |
| hash iteration order | 哈希遍历顺序 | 不是把元素进行排序；标题中的 Hash Ordering 也按这一语境处理。第148–194行。 |
| hash flooding | 哈希洪水攻击 | 与脚注中的拒绝服务攻击说明对应。第167–186行。 |
| transitive closure | 传递闭包 | 保留正式术语，表示直接依赖继续向下展开得到的依赖范围。第214–216行。 |
| backward compatibility | 向后兼容性 | 保证旧用法仍能工作，不保证旧优化在新硬件上仍然有效。第210–212行。 |
| churn / Churn Rule | 变更适配负担／变更适配规则 | “变更适配规则”是本章根据规则内容采用的解释性译名，并非声称存在统一官方中文名；不是人员流失。第262–264行。 |
| Beyoncé Rule | 碧昂斯规则 | 沿用现有专名，强调依赖行为应由统一 CI 测试覆盖。第276–286行。 |
| regression | 回归缺陷 | 指变更导致原有功能失效，不是回退或回滚操作。第298–300行。 |
| toil | 琐务 | SRE 语境的重复性工作，保留英文以便与后续术语体系衔接。第321–346行。 |
| shift left | 左移 | 把问题发现提前到开发工作流的早期，以降低修复成本。第352–366行。 |
| canary | 金丝雀发布 | 本章指发布阶段，不只译为“金丝雀”。第354–356行。 |
| consensus / unanimity | 共识／全体一致 | 原文明确区分二者，不把共识写成人人赞同。第370–372行。 |
| escalation path | 升级处理渠道 | 指决策有争议时向相应负责人升级处理，不是软件升级路径。第370–372行。 |
| opportunity cost | 机会成本 | 考虑不采取某项行动或占用工程师时间而放弃的其他产出。第375–450行。 |
| gibibytes | GiB | 原文明确为 five gibibytes，改为5 GiB；不再使用原译的5Gb。第448–450行。 |
| fork / branch | 分叉／分支 | fork 指另行维护派生实现，branch 指版本控制分支；避免把 branch 译成“分支机构”。第266–268、484–503行。 |
| semantic versioning / SemVer | 语义化版本管理 | 与一般的版本控制区分。第525–527行。 |
| Continuous Deployment / CD | 持续部署 | 第525行确实写的是 Deployment，不能因第24章标题为 Delivery 就自行统一成持续交付。 |

## 保留的原文疑点

- 第136行：官方在线版包含本地缺失的从句，中文已据此校正，本地英文未补写。
- 第501行：`project-time boundaries` 在官方在线版中也是这一表述。本章暂保留接近字面的译法，不擅自改成 `project/team` 或“跨团队边界”。语义仍可在后续校对时讨论。
- 第244行脚注强调人际交互量的次线性增长，而提要第545行写 linear or better。本次保留两处各自的限定，不自行把原著表述合并成同一标准。
